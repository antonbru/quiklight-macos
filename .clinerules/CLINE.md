# CLINE.md — QuikLight macOS: управление LED-подсветкой монитора

> Этот файл — главный документ для Cline. Читай его первым, затем `docs/PROTOCOL.md` (обязательно, полностью), `docs/REFERENCES.md` и `docs/ARCHITECTURE.md` (карта модулей проекта).

## 1. Роль

Ты — инженер, которому поручено разработать нативное macOS-приложение для управления LED-подсветкой монитора Robobloq QuikLight (она же Feelin Light Q1), которая сейчас управляется официальным приложением **SyncLight** (Electron, Windows + macOS preview, тяжёлое: ~430 МБ RAM, 5 процессов).

Наша цель — **своё лёгкое нативное приложение**: menu bar app, которое умеет:
1. статичный цвет, яркость, встроенные эффекты, выключение;
2. **screen sync** — синхронизация цвета ленты с краями экрана (ambilight) в реальном времени;
3. (опционально, позже) sound reactive — реакция на звук с компьютера.

Протокол устройства **уже полностью расшифрован** (см. `docs/PROTOCOL.md`) и верифицирован байт-в-байт тремя независимыми open-source реализациями (см. `docs/REFERENCES.md`). **Ничего реверс-инжинирить с нуля не нужно** — только реализовать на macOS.

## 2. Железо

| Параметр | Значение |
|---|---|
| Устройство | Robobloq QuikLight / Feelin Light Q1 (USB LED-панель для монитора) |
| Vendor ID | `0x1A86` (QinHeng/WCH) |
| Product ID | `0xFE07` |
| Manufacturer string | `ROBOBLOQ` |
| Product string | `USBHID` |
| Интерфейс 0 | HID generic, endpoints 64 байта — **канал управления** |
| Интерфейс 1 | HID keyboard — сенсорные кнопки панели (команды цвета **игнорирует**, не путать) |
| Лента | **51 LED** (24" панель; проверено `readDeviceInfo`). Раскладка по умолчанию — авто-пропорции 17/29/17 под фактическое число LED (см. §6) |
| Подключение | USB-кабель, plug & play, драйверы не нужны (стандартный HID) |

⚠️ **Фаза 0 — обязательная проверка железа.** Прежде чем писать код, на машине с подключённой панелью выполни:
```bash
system_profiler SPUSBDataType | grep -A 8 -i robobloq
# или
ioreg -p IOUSB -l -w 0 | grep -i -A 6 robobloq
```
Ожидаемый результат: устройство с idVendor `1a86`, idProduct `fe07`, manufacturer `ROBOBLOQ`.

**Если устройство НЕ найдено или подключается по Bluetooth/донглу — ОСТАНОВИСЬ.** BLE-вариант использует другой протокол (адресация по MAC, 20-байтные кадры, модуль `62564` из SyncLight) — он в этом проекте **не реализуется**, вернись к владельцу за уточнением.

## 3. Стек и архитектура (решение принято 14.08.2026)

| Решение | Значение | Почему |
|---|---|---|
| Язык | **Rust** (edition 2021/2024, стабильный канал) | Главный референс SyncRGB уже на Rust — переносим протокол и цветообработку почти 1-в-1. Безопасность памяти, нулевой рантайм, лёгкий вес |
| Целевая macOS | 13.0+ (Ventura) | ScreenCaptureKit требует 12.3+; берём 13+ для современных API |
| GUI | **AppKit через крейт `objc2`** (`NSStatusItem` в menu bar, `NSWindow` для настроек) | Нативный GUI без Xcode-проектов: AppKit доступен из Rust через objc2, вес ~10–20 МБ RAM. SwiftUI требует полноценный Xcode, которого у владельца нет |
| Захват экрана | ScreenCaptureKit через крейт **`objc2-screen-capture-kit`** (`SCScreenshotManager`, macOS 14+) | Периодический захват CGImage проще и надёжнее в objc2, чем `SCStream`; см. Фазу 2 |
| HID-транспорт | Крейт **`hidapi`** (`hidapi` crate, обёртка над системной IOKit) | Тот же крейт, что использует SyncRGB — проверенный путь |
| Сборка | **Cargo workspace** (БЕЗ .xcodeproj) + скрипт сборки `.app`-бандла | Воспроизводимо, дружелюбно к агентам, не требует Xcode GUI. Для ScreenCaptureKit достаточно SDK из Command Line Tools |
| Тесты | `cargo test`: юнит-тесты протокола (построение/парсинг пакетов, checksum, чанкинг) без железа | Железо не всегда под рукой у CI |
| Альтернативы, отклонённые | Swift/SwiftUI (нужен полноценный Xcode), Electron/Tauri/Flutter (запрещены CLINE.md — тяжёлые), Python+PyObjC (~40–60 МБ RAM, слаб для 30–50 fps) | См. решение владельца от 14.08.2026 |

Юнит-тесты лежат **inline** в модулях (`#[cfg(test)] mod tests`), отдельного каталога `tests/` нет.

Модель потоков (реализовано): один фоновый поток (`engine`) владеет HID-устройством и выполняет режимы; UI общается с ним через `std::sync::mpsc` — команды (`Command`) туда, события (`WorkerEvent`) обратно. Непрерывные режимы (screen sync, «Камин») тикают по `recv_timeout` с интервалом из настроек; запись в HID строго последовательная — чанки одного кадра не перемежаются. UI опрашивает события таймером 0.25 с. Дублирующая логика (выключение 0x97×4+чёрный, сборка SC-кадра) живёт в `quiklight-core`.

Каждая фаза = готовый, проверенный результат. Не переходи к следующей, пока не выполнены критерии. Спрашивай владельца только по открытым вопросам (раздел 6), всё остальное решай сам в рамках решений выше.

### Фаза 0 — Разведка железа (до написания основного кода)
- [x] `hidprobe` CLI: находит устройство `1a86:fe07`, открывает interface 0, шлёт `readDeviceInfo` (0x82), парсит и печатает: MAC, число LED, версию прошивки
- [x] CLI умеет: `color R G B`, `brightness 0-100`, `off`, `effect <type> <index>` — проверить, что панель реагирует
- [x] Проверено: статичный цвет загорается, яркость меняется, панель гаснет
- **Критерий перехода:** панель отвечает и управляется командами. Если панель не найдена / BLE — стоп, вопрос владельцу.

### Фаза 1 — quiklight-core (библиотека, без экрана)
- [x] `packet.rs` + `actions.rs`: все команды из `docs/PROTOCOL.md` (цвет, яркость, эффекты, скорость, выкл, info)
- [x] Юнит-тесты: корректный checksum, чанкинг >64 байт, парсинг ответа `readDeviceInfo`, эталонные hex-пакеты из `docs/PROTOCOL.md` (пересчитанные программно!)
- [x] HID-слой на `hidapi`: поиск по VID/PID, открытие interface 0 (не 1!), запись с report ID 0x00, последовательная очередь записи
- [x] Команды с ответом (`write_with_response`): задержка ~200 мс перед чтением, таймаут чтения 500 мс (по образцу SyncRGB)

### Фаза 2 — Screen sync
> **Решение (14.08.2026):** захват реализован через `SCScreenshotManager` (периодический
> захват CGImage), а не `SCStream` — это заметно проще и надёжнее в objc2, но требует
> **macOS 14+**. На macOS 13 приложение корректно сообщает об ограничении; статичные
> режимы и эффекты работают везде.
- [x] `screen_capturer.rs` через ScreenCaptureKit (objc2): захват главного дисплея (≤480 px по большой стороне, BGRA, pitch)
- [x] `color_extractor.rs` + `led_mapper.rs`: кадр → сетка по соотношению сторон → средний цвет ячеек; края top/left/right (+bottom, если задан в раскладке), чёрный край подменяется ближайшей внутренней строкой; маппинг на LED в порядке проводов (число LED — из `readDeviceInfo`)
- [x] Отправка SC-пакетов (action 0x80) настраиваемо 20–60 fps (интервал 16–50 мс, по умолчанию 30); постобработка: гамма, насыщенность, сглаживание, light compression (по образцу SyncRGB `extractor.rs`)
- [x] Правильная остановка: при выходе из приложения — выключить LED (0x97) или вернуть последний статичный цвет
- **Критерий перехода:** цвета краёв экрана повторяются лентой без видимой задержки; CPU при синке < 10% на современном Mac; RAM < 40 МБ (ориентир: SyncRGB на Windows — 58 МБ, официальный SyncLight — 430 МБ; Rust без рантайма должен быть легче)

- [x] Окно настроек (`NSWindow` через AppKit/objc2): число LED (0 = авто), раскладка по краям, fps, гамма, насыщенность, сглаживание, light compression, «выключать LED при выходе»

- [x] Свой эффект «Камин»: мерцающее пламя по нижней части ленты (SC-кадры ~30 fps)

## 5. Правила работы

1. **Читай `docs/PROTOCOL.md` полностью перед написанием кода протокола.** Там есть подводные камни (интерфейс 1 игнорирует команды; скорость эффектов инвертирована; `254` = «до конца ленты»; LED нумеруются с 1; старые прошивки не знают 0x97 — гасить чёрным цветом).
2. **Не реализуй**: BLE-вариант (MAC-адресация), протокол клавиатур/мышей Robobloq (CRC16, заголовок SC для клавиатур) — это другие протоколы, нам не нужны.
3. **Не добавляй тяжёлые зависимости.** Никакого Electron/Tauri/Flutter. Целевой вес приложения — десятки МБ RAM (ориентир 10–40 МБ), не сотни.
4. **Официальный SyncLight во время разработки лучше закрыть** — два приложения не должны одновременно писать в HID-устройство.
5. **Юнит-тесты протокола обязательны** — они не требуют железа и ловят ошибки кодирования (checksum, порядок байт, чанкинг).
6. Коммиты — маленькие, с осмысленными сообщениями. Git-репозиторий инициализируй в корне проекта.
7. Если обнаружишь, что что-то в `docs/PROTOCOL.md` не совпадает с реальным поведением панели — зафиксируй в `docs/` и сообщи владельцу, но сначала перепроверь (ошибка скорее в коде, чем в протоколе — он верифицирован тремя реализациями).
